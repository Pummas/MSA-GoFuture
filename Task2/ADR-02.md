# ADR-02: Событийная платформа, Saga и потоковая обработка GoFuture

## Общая информация

1. **Автор ADR** — Лукин М.А.
2. **Статус** — На согласовании
3. **Согласующие** — продуктовая команда GoFuture

## Контекст

В целевой архитектуре из [Task1/ADR-01.md](../Task1/ADR-01.md) домены Booking, Driver, Pricing, Payments, Fraud, Notification, Geography и Analytics владеют собственными данными. Между ними нужно передавать факты о поездках, платежах и телеметрии без общей транзакции и без прямого доступа к чужим БД.

Поток должен одновременно поддерживать:

- критический процесс заказа поездки и авторизации платежа;
- высокочастотные обновления местоположения водителей и пакетную телеметрию;
- повторную обработку, аудит и воспроизводимость аналитики;
- постепенную миграцию монолита Django, где RabbitMQ и Celery используются только в переходном контуре;
- независимое масштабирование по абстрактному `region_id`, не связывая архитектуру с конкретными географическими названиями.

Нужны единый контракт события, гарантии публикации при сбое сервиса, управление согласованностью с помощью саги, сохранение порядка событий агрегата, повторная обработка и наблюдаемость всего пути от API до потребителя или Flink.

### Модель доменных событий

Событие — неизменяемый факт, опубликованный владельцем агрегата после успешной бизнес-транзакции. Команды саги (`ReserveDriver`, `AuthorizePayment`, `CapturePayment`, `CancelBooking`) отделены от фактов (`BookingCreated`, `PaymentAuthorized`): у команд отдельные топики или тип сообщения и связь с экземпляром саги.

Минимальный набор фактов:

| Домен | События | Ключ агрегата |
|---|---|---|
| Booking/Trip | `BookingCreated`, `BookingCancelled`, `DriverAssigned`, `TripStarted`, `TripCompleted`, `TripCancelled` | `booking_id` |
| Driver | `DriverAvailabilityChanged`, `DriverLocationUpdated`, `DriverLocationBatch`, `DriverAssignmentAccepted`, `DriverAssignmentRejected` | `driver_id` |
| Pricing | `QuoteCalculated`, `SurgeMultiplierUpdated` | `booking_id` или `region_id` для фонового расчёта |
| Payments | `PaymentAuthorizationRequested`, `PaymentAuthorized`, `PaymentAuthorizationFailed`, `PaymentCaptured`, `PaymentRefunded` | `payment_id` |
| Fraud | `FraudCheckCompleted`, `FraudReviewRequired` | `booking_id`/`payment_id` |
| Notification | `NotificationRequested`, `NotificationDelivered`, `NotificationFailed` | `notification_id` |
| Geography | `RouteCalculated`, `DriverRegionChanged` | `booking_id`/`driver_id` |

`DriverLocationUpdated` используется для одной позиции, `DriverLocationBatch` — для пакета позиций с монотонно возрастающими версиями или временем измерения. Высокочастотная телеметрия является документированным исключением из Transactional Outbox/CDC: эти два типа событий публикуются напрямую идемпотентным producer'ом Driver. Гарантии — at-least-once и идемпотентный эффект у потребителя; потеря допустима только при полном отказе регионального Kafka-кластера согласно этому ADR. Для остальных доменных событий действует Transactional Outbox/CDC.

### Event envelope

Каждое сообщение Kafka содержит версионированную оболочку события и типизированную полезную нагрузку (`payload`):

```json
{
  "event_id": "uuid",
  "event_type": "BookingCreated",
  "occurred_at": "2026-01-01T00:00:00Z",
  "trace_id": "trace-id",
  "causation_id": "event-or-command-id",
  "tenant_id": "tenant-uuid",
  "region_id": "abstract-region-id",
  "schema_version": 1,
  "payload": {}
}
```

`event_id` уникален в пределах платформы. `causation_id` связывает факт с командой или предшествующим событием, `trace_id` проходит через HTTP, Kafka и Flink. `tenant_id` — стабильный непрозрачный идентификатор арендатора; он проверяется на Gateway, у производителя и потребителя события. В `payload` находятся только данные контракта домена, без секретов и платёжных реквизитов. Schema Registry хранит схемы Avro и JSON Schema, проверяет совместимость и запрещает несовместимые изменения в поддерживаемой версии.

## Рассмотренные варианты

### Вариант №1 «Kafka как целевая шина событий»

Доменные сервисы публикуют события в Kafka через Transactional Outbox и CDC с Debezium. Kafka обеспечивает надёжный журнал, группы потребителей, повторное чтение и независимость потребителей. Flink читает те же топики для обработки по окнам. RabbitMQ и Celery обслуживают ещё не перенесённые задачи; после миграции этот контур выводится из эксплуатации.

### Вариант №2 «RabbitMQ/Celery как постоянная шина»

Сохранить текущий контур AMQP и добавить очереди для новых сервисов. Это сокращает объём начальной миграции, но затрудняет повторную обработку за длительный период, независимое чтение, обработку потока по окнам и единое масштабирование телеметрии. Связи с прежним контуром сохраняют общую область влияния отказов.

### Вариант №3 «Синхронные REST-вызовы без шины событий»

Booking вызывает домены последовательно, а аналитика читает реплики. Подход прост для схемы «запрос — ответ», но связывает доступность сервисов, усложняет компенсации, не сохраняет историю фактов и не подходит для `DriverLocationBatch`, повторной обработки и Flink.

## Сравнение альтернатив

| Вариант решения | Преимущества | Недостатки |
|---|---|---|
| №1 «Kafka + Outbox/CDC» | надёжный журнал, повторное чтение, группы потребителей, потоковая обработка, изоляция производителей и потребителей | стоимость эксплуатации Kafka и Schema Registry; согласованность достигается со временем; нужны DLQ, идемпотентность и контроль схем |
| №2 «RabbitMQ/Celery» | знакомая инфраструктура, низкий порог миграции, удобство для фоновых задач | нет полноценного журнала и повторного чтения; сложнее рассылать события нескольким получателям и обрабатывать поток по окнам; старый контур остаётся критической зависимостью |
| №3 «REST» | понятная модель синхронных вызовов и быстрый ответ | каскадные отказы; нет независимой повторной обработки; телеметрия плохо масштабируется; нужны распределённые транзакции |

## Принятое решение

Принят **вариант №1 — Kafka как целевой брокер событий, Transactional Outbox и CDC с Debezium, оркестрируемая сага и Flink для потоковой обработки**. RabbitMQ и Celery обслуживают только ещё не перенесённые задачи и не являются источником новых междоменных событий.

### Реестр топиков и правила Kafka

Схема имени топика: `{domain}.{aggregate}.{purpose}.v{schema_version}`. В рабочей среде топики разделены по региональным кластерам; в сообщении всегда есть `region_id`. Топология не содержит конкретных географических названий.

| Топик | Основные события и сообщения | Производитель | Группы потребителей | Ключ | Срок хранения |
|---|---|---|---|---|---|
| `booking.trip.lifecycle.v1` | `BookingCreated`, `DriverAssigned`, `TripStarted`, `TripCompleted`, события отмены | Booking | `booking-projections`, `notification`, `analytics`, `flink-surge` | `region_id:tenant_id:aggregate_id` | 7 дней |
| `driver.location.telemetry.v1` | `DriverLocationUpdated`, `DriverLocationBatch` | Driver | `flink-geo`, `flink-surge`, `flink-fraud`, `analytics` | `region_id:tenant_id:aggregate_id` (для телеметрии — `driver_id`, внутри пакета последовательность по водителю) | 24 часа |
| `driver.assignment.result.v1` | `accepted` (принято), `rejected` (отклонено), `no-driver` (водитель не найден) | Driver | `booking-saga`, `analytics` | `region_id:tenant_id:aggregate_id` | 7 дней |
| `pricing.quote.events.v1` | `QuoteCalculated`, `QuoteExpired` | Pricing | `booking-saga`, `analytics` | `region_id:tenant_id:aggregate_id` | 3 дня |
| `pricing.surge.updates.v1` | `SurgeMultiplierUpdated` | Pricing и Flink | `booking`, `driver`, `analytics` | `region_id:tenant_id:aggregate_id` | 3 дня |
| `payments.transaction.status.v1` | `PaymentAuthorized` (авторизация), `Failed` (ошибка), `Captured` (списание), `Refunded` (возврат) | Payments | `booking-saga`, `notification`, `analytics`, `flink-fraud` | `region_id:tenant_id:aggregate_id` | 30 дней |
| `fraud.assessment.result.v1` | `FraudCheckCompleted`, `FraudReviewRequired` | Fraud | `booking-saga`, `analytics` | `region_id:tenant_id:aggregate_id` | 30 дней |
| `notification.delivery.status.v1` | `Requested` (запрос доставки), `Delivered` (доставлено), `Failed` (ошибка) | Notification | `analytics` | `region_id:tenant_id:aggregate_id` | 7 дней |
| `geography.route.events.v1` | `RouteCalculated`, `DriverRegionChanged` | Geography | `booking-saga`, `driver`, `analytics` | `region_id:tenant_id:aggregate_id` | 7 дней |
| `saga.booking.command.v1` | Команды и ответы оркестратора саги Booking | Booking / Saga | `driver-saga-endpoint`, `payments-saga-endpoint`, `fraud-saga-endpoint` | `region_id:tenant_id:saga_id` | 7 дней |
| `{domain}.retry.{n}.v1` и `{domain}.dlq.v1` | Отложенная повторная доставка и необрабатываемые сообщения | Потребители платформы | Обработчик повторных попыток и команда эксплуатации | Тот же ключ, что у исходного сообщения | Топик повторов — 1 день; DLQ — 30 дней |

События распределяются по партициям на основе ключа `region_id:tenant_id:aggregate_id` по однозначному правилу внутри регионального кластера. Этот составной ключ сохраняет порядок событий по `aggregate_id`, обеспечивает tenant isolation и применение квот арендатора; для Saga допустимо исключение `region_id:tenant_id:saga_id`. События разных агрегатов, арендаторов и регионов могут обрабатываться параллельно. Число партиций и срок хранения уточняются по результатам замера нагрузки; добавление партиций не должно менять порядок событий внутри агрегата.

Производитель использует `acks=all`, идемпотентную публикацию и коэффициент репликации, согласованный с SLO. Группы потребителей имеют независимые смещения и могут перечитать поток с контрольной точки. Повторная обработка выполняется в отдельной группе или проекции, не затрагивая действующие операции без ключа идемпотентности.

### Надёжная доставка и обработка ошибок

1. Для обычного доменного события сервис в одной локальной транзакции записывает бизнес-изменение и строку `outbox_events` с оболочкой события, топиком, ключом и версией схемы. `DriverLocationUpdated` и `DriverLocationBatch` публикуются напрямую идемпотентным producer'ом как документированное исключение для высокочастотной телеметрии; для них сохраняются at-least-once и идемпотентный эффект, а потеря допустима только при полном отказе регионального Kafka-кластера.
2. Debezium и Kafka Connect читают WAL через CDC, а Outbox Event Router публикует запись в Kafka. Публикация с периодическим опросом — временный резервный способ. Повтор CDC безопасен благодаря `event_id`.
3. Потребитель хранит журнал обработанных событий с уникальным `(consumer_name, event_id)` либо применяет идемпотентный бизнес-ключ. Смещение фиксируется только после успешного выполнения операции.
4. При временных ошибках доставка повторяется с увеличением задержки и случайным разбросом, например 2 с → 20 с → 3 мин → 15 мин. Сообщения топика повторов обрабатываются последовательно по ключу. После исчерпания попыток сообщение попадает в `{domain}.dlq.v1` с причиной и исходным смещением.
5. Для DLQ назначается ответственный и настраивается оповещение. После исправления ответственный безопасно запускает повторную обработку вручную. `payload` не правится: исправление оформляется новым событием. Сообщения с ошибками схемы не доходят до потребителя и не теряются.
6. Для опоздавших и пришедших не по порядку событий используются `occurred_at`, версия агрегата, отметка прогресса и правила окон Flink. Более старая версия не перезаписывает новую.

### Saga: оркестрация Booking и Payments

Оркестратор саги Booking хранит `saga_id`, состояние и журнал шагов, отправляет команды и принимает события. Payments использует собственную сагу Payment Saga для безопасного взаимодействия с PSP. Отдельный сервис Payouts не вводится.

| Шаг | Команда и событие успеха | Действие при ошибке и компенсация |
|---|---|---|
| 1 | `CreateBooking` → `BookingCreated` | Не создавать активную сагу |
| 2 | `CalculateQuote` → `QuoteCalculated` | Опубликовать `BookingRejected` или повторить расчёт |
| 3 | `CheckFraud` → `FraudCheckCompleted` | Отклонить заказ (`reject`) или отправить на ручную проверку, переведя в состояние ожидания (`hold`) |
| 4 | `ReserveDriver` → `DriverAssigned` | Повторить с отсечением дубликатов; при исчерпании попыток — `BookingCancelled` |
| 5 | `AuthorizePayment` → `PaymentAuthorized` | Отменить назначение водителя; опубликовать `BookingCancelled` |
| 6 | `StartTrip` → `TripStarted` | Отменить поездку до начала и снять резерв средств |
| 7 | `CapturePayment` → `PaymentCaptured` после `TripCompleted` | Повторить попытку подтверждения списания; если это невозможно, открыть финансовое расследование или провести сверку. Повторное списание запрещено |
| 8 | `CompleteBooking` → `TripCompleted` / `BookingCompleted` | Повторить завершение заказа, не откатывая уже завершённую поездку |

Компенсации выполняются только для обратимых шагов: отмены назначения водителя, отмены авторизации или снятия резерва средств. Списание, завершение поездки и запись в платёжный реестр необратимы. Их исправляют отдельной финансовой операцией — возвратом или сверкой, а не откатом БД. Истечение времени ожидания, размыкание цепи и переход в ограниченный режим не должны создавать новую оплату.

Для простых процессов применяется хореография: Notification подписывается на `TripStarted`, `TripCompleted`, `PaymentFailed`, а Analytics — на весь реестр. Driver и Geography обновляют проекции по телеметрии. Для критического процесса заказа хореография не используется: в централизованном автомате состояний лучше видны сроки ожидания, повторы и компенсации.

### Flink и consumer groups

Flink работает в региональном кластере и читает Kafka через отдельные группы: `flink-geo` строит геоиндекс из пакетов координат, `flink-surge` рассчитывает спрос и предложение по временным окнам, `flink-fraud` готовит потоковые признаки, `flink-analytics` обновляет витрины почти в реальном времени. Для задач обязательны контрольные точки в надёжном хранилище, отметки прогресса, метрики обратного давления и гарантия однократного изменения состояния. Записи во внешние системы остаются идемпотентными.

Для саги Booking, Notification и Analytics выделяются отдельные группы потребителей, чтобы отставание аналитики не блокировало заказ. Число экземпляров можно увеличивать до числа партиций. SLI потоков — отставание потребителей, задержка обработки и возраст самого старого сообщения.

### Observability и метрики

Сервисы, Debezium, клиенты Kafka и Flink передают телеметрию через OpenTelemetry. Структурированные журналы содержат `trace_id`, `event_id`, `saga_id`, `region_id`, топик, партицию и смещение, но не персональные данные и платёжные секреты. Tempo хранит трассы, Loki — журналы, Prometheus — метрики, Grafana показывает панели мониторинга, Alertmanager направляет оповещения. Kafka, PostgreSQL, Debezium и Flink используют средства экспорта метрик.

| Класс | Метрики |
|---|---|
| Технические | Загрузка процессора, памяти, диска и сети; запросы в секунду (RPS); частота ошибок; задержка p95 и p99; блокировки и соединения БД; доступность брокеров Kafka; ошибки производителей; ISR и партиции с недостаточным числом реплик; входящие и исходящие байты и сообщения |
| Потоковые | Отставание потребителя и возраст старейшего сообщения по группе, топику и региону; сквозная задержка события; накопление исходящих событий; отставание CDC; частота повторов; размер и темп пополнения DLQ; объём повторной обработки; время и сбои создания контрольных точек Flink; обратное давление; отставание отметки прогресса; отброшенные события и события не по порядку |
| Саги | Активные саги; задержка шагов; число истечений времени ожидания, повторов и компенсаций; зависшие саги; время от авторизации до списания; число дубликатов команд и событий; очередь на сверку |
| Бизнес-показатели | Созданные, отменённые и завершённые поездки; время до назначения и начала; доступные водители; успешность расчёта котировок; исходы платежей (`PaymentAuthorized` / `Captured` / `Refunded` / `Failed`); суммы и расхождения платёжного реестра; успешные и неуспешные доставки; конверсия; доля заказов в ограниченном режиме |

Критические оповещения срабатывают, если отставание потребителей превышает SLO, останавливается обработка исходящих событий или CDC, не хватает реплик партиций, резко растёт DLQ, зависает сага, расходятся данные реестра Payments и PSP или теряются события. В Grafana есть отдельные панели Platform, Kafka/consumer groups, Flink, Saga, Payments и Business KPI.

## Компромиссы

- Kafka и Schema Registry дают повторную обработку и рассылку нескольким потребителям, но увеличивают затраты на кластеры, планирование ёмкости и управление схемами.
- Согласованность со временем и доставка как минимум один раз требуют журналов обработанных и исходящих событий, отсечения дубликатов, DLQ и эксплуатационной инструкции. Зато сервисы не блокируют друг друга общей транзакцией.
- Оркестратор увеличивает центральную сложность Booking, но делает компенсации и состояние критического процесса наблюдаемыми.
- Одновременная эксплуатация Kafka и RabbitMQ/Celery усложняет миграцию. Срок вывода контура и метрика трафика монолита (`legacy traffic`) не дают переходному контуру стать постоянным.
- Разбиение по `region_id` изолирует нагрузку и отказы, но требует резерва мощности и отдельного плана повторной обработки и аварийного восстановления регионального кластера.

| Риск | Мера |
|---|---|
| Дубликат или потеря события | Transactional Outbox, Debezium, `event_id`, журнал обработанных событий, сверка и оповещения об отставании таблицы исходящих событий и CDC; для высокочастотной телеметрии — идемпотентный producer и допустимая потеря только при полном отказе регионального Kafka-кластера |
| Нарушение порядка | Ключ `region_id:tenant_id:aggregate_id`, версия агрегата и последовательные повторы по ключу |
| Необрабатываемое сообщение или бесконечные повторы | Ограниченные повторы с увеличением задержки, DLQ, назначенный ответственный и контролируемая повторная обработка |
| Двойное списание | Ключ идемпотентности, уникальный идентификатор операции у поставщика, реестр Payments и сверка с PSP |
| Зависшая сага | Надёжное хранение состояния, команда по истечении времени ожидания, компенсация, панель мониторинга и инструкция для ручного вмешательства |
| Перегруженная партиция или переполнение потока телеметрии | Пакетные события, квоты, проверка пропускной способности партиции, обратное давление и правила хранения |
| Несовместимая схема | Schema Registry, проверка совместимости в CI, `schema_version` и версионирование топиков |
| Утечка персональных данных через полезную нагрузку или журналы | Классификация данных, маскирование, шифрование и TLS, ACL Kafka и минимальные права потребителей |
| Недоступность региона | Репликация, план аварийного восстановления Kafka и данных, региональная изоляция и повторная обработка после восстановления |

Исходные показатели ёмкости, топология репликации и точные сроки хранения утверждаются после нагрузочного теста. Это не меняет выбор Kafka, Outbox и CDC, саг и средств наблюдаемости.
